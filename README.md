# FedEx-inspired shipping website

React + TypeScript + Vite application in `app/`, with existing shipping, tracking, print, locations, account, dashboard, supplies, returns, and admin preview pages.

## Run locally

```sh
cd app
npm ci
npm run dev
```

Vite listens on `0.0.0.0:5173` and accepts Arena's `.e2b.app` preview hosts. Browser requests use same-origin URLs; no browser-facing localhost API URLs were added.

## Interior pages and local service tools

- Shipping, Design & Print, Locations, Support, rates, and pickup planning share the reference-style layout and locally hosted genuine photographs. Eight additional FedEx Office photos and their provenance are included; no generated interior-page imagery was added.
- Shipping validates ZIP codes and a positive parcel weight, then transfers the details into the sample rate calculator. Optional dimensions change the illustrative estimates. A chosen service, date, ZIP codes, and package details prefill the existing shipment wizard, which uses the same local price formula.
- `/shipping/pickup` validates a date, package count, and local time window, then produces a pickup plan. It does **not** book a pickup; official FedEx booking links complete the handoff.
- Design & Print selects a product, checks an optional PDF/JPG/PNG filename/type/size (20 MB maximum), and downloads a local text brief. No file content is uploaded, previewed, or sent to FedEx Office, and no print order is placed. Official product links let users continue on FedEx Office.
- Locations replaces fictional records and the fake map with five verified New York examples. Search and type filters operate on this explicitly curated snapshot. Official listings, public phone numbers, and real map links provide the handoff; current hours, distances, geolocation, and a complete directory are not simulated.
- Support searches local FAQ articles and filters topics, with native keyboard-operable disclosures. Its button opens the existing sample assistant. Assistant responses link to useful tools and never claim to connect to a live agent.
- Tracking's Delivery Manager and mobile-app buttons link to actual official destinations. Upload controls now live in the rebuilt administration workspace; the existing serverless API contracts and their separate server-secret authorization are unchanged.

Real pricing, delivery commitments, account actions, pickup reservations, printing orders, and claims remain on the official FedEx sites. These local tools are explicitly independent previews.

## Supplies and return-preparation refresh

Files and notes stay in the current page session; no photo bytes or return plan are posted or persisted. A brief contains photo filenames/byte counts only, not image contents.

## Personal and administrator workspaces

- Updated wording across UI, document title, downloads, accessibility labels, helpers, and tests while preserving explicit non-live-service and independent-project disclosures.
- `/login` supports creating a local profile and signing back in with a verified workspace passphrase. `/dashboard` provides an empty-first overview, searchable shipment-plan CRUD/status controls, filtered exports, a local address book with a preferred default, profile editing, passphrase changes, and truthful official-carrier handoffs. Normal profiles are not preloaded with shipment data, saved cards, billing activity, or rewards balances.
- Browser-local `/login` also offers a clearly labeled **Demo login**. One click creates/reopens a member-only `Demo User` (`demo@workspace.local`) with two sample shipment plans, two saved addresses, recent-plan tracking links, and a dashboard tracking monitor for `LOCAL-12345`. The demo profile has no passphrase, salt, or digest; its email stays fixed, it cannot be used through the passphrase form, and changing its stored role does not grant administrator access. Seeding is idempotent and preserves separate local profiles. In server mode the one-click option is hidden and verified account sign-in remains required. A separate **Admin login** entry on the same screen links to the credentials-based administrator sign-in and, while no credentialed local administrator exists, also offers **One-click admin login** for a separate browser-local `Demo Administrator` (`demo-admin@workspace.local`). That admin demo has no passphrase, salt, or digest, cannot authorize server/API or private-image actions, and is removed/unavailable once a credentialed local administrator is created.
- `/admin/login` sets up the first administrator with an owner-chosen passphrase; there is no default administrator password. `/admin/settings` shows actual local record totals and activity, reviews all local plans, filters and suspends/activates member profiles, saves a workspace name/announcement, and exports records without credential hashes or salts. Its Overview also summarizes public-shipment operations (active, in-transit/out-for-delivery, on-hold, and delivered totals), lists shipments that need attention (on hold with their public issue, or hidden from public tracking) and the most recently updated shipments with tracking links, and offers quick actions into each section; recent activity can expand beyond the latest eight entries. Workspace profiles additionally show each profile’s assigned shipment/plan/address counts, server-mode email-verification state, and an expandable list of that profile’s assigned shipments.
- A free, fully local **sample address generator** (no external API) invents plausible US addresses from common street names and real city/state/ZIP combinations. Members can auto-generate and save an address from the address book or address editor, administrators can auto-fill a route when creating a shipment, and **Generate trackable route** creates an in-transit public shipment from a generated origin → destination pair in one click so the route can be monitored on the public tracking page. Generated addresses are clearly labeled samples — they are not verified or deliverable addresses, and generated routes are application records, not FedEx shipments. Administrators can enable **automatic route progression** on any public shipment (in the shipment editor or Shipment operations) so the application advances it Label created → Picked up → In transit → Out for delivery → Delivered on a chosen interval (1 minute to 24 hours); each automatic event is labeled “Automatic update generated by this application — not a carrier scan” on the public page, progression pauses on any manual status change/event correction/removal/undo, while on hold, or while archived, and stops permanently at Delivered.
- The administrator dashboard’s **Public shipments** section creates a separate public-safe shipment registry. An administrator chooses a workspace customer or a guest/customer label, enters the public recipient label, city/state/ZIP route, service, dates, status, and current location, and either supplies or generates a unique tracking number. Generated application numbers mimic common FedEx lengths—15 digits for Ground and 12 digits for Express-style services—but they are not issued or validated by FedEx. Grouped 12/15-digit entries are stored as digits. Administrators can manually change a shipment’s status directly from the table’s status dropdown and **Save status**, or use **Modify status** to set the status together with location, event time, and a public note. Choosing **On hold** requires one of 42 public-safe hold reasons grouped by address/recipient, customs/regulatory, package/documents, facility/transport, weather/external events, and account/other issues; the table, detailed status editor, shipment editor, and timeline-event correction all use the same reason picker. **Shipment operations** opens a detail view for correcting or removing timeline events, undoing the latest update, saving an administrator-only internal note, duplicating a shipment with a new generated tracking number, archiving/restoring it, and toggling public tracking from the table or detail view. When setting **In transit** or **Delivered**—from the table status editor, **Modify status**, the shipment editor, or a timeline-event correction—the administrator can attach an optional public stage photo; it is downscaled and compressed in the browser, stored on that timeline event, and shown beside that stage on the public journey, in Travel history, and in the tracking summary. Archived shipments are hidden from guests and assigned customers until restored. The record can also be edited or permanently removed, and **Copy public tracking link** / **View public tracking** opens `/tracking?number=...`. Street addresses, email addresses, private notes, account identifiers, and private image attachments are never part of the public record.
- A visitor does not need to sign in to track a public shipment. The tracking page shows only the administrator-entered public status, route, service, estimated delivery, public note, event history, and any administrator-attached In transit/Delivered stage photos (captioned as application-record photos, not carrier delivery proof). When the current status is **On hold**, the selected reason is displayed directly in a prominent “Shipment on hold” issue alert above the summary, in the current journey event, and in Shipment facts; releasing the hold clears the current alert while the historical hold event remains in the timeline. Once a shipment is **Delivered**, the journey and Travel history show the complete route (Label created → Picked up → In transit → Out for delivery → Delivered) even when the administrator jumped straight from In transit to Delivered; stages without a recorded update are marked “route completed” rather than given invented scan times. An assigned customer also sees the current hold issue under **Shipments created for you** in their workspace. Unknown tracking numbers now show a clear not-found state instead of an invented delivered timeline. These are application-managed records, not FedEx bookings, labels, payments, or live carrier scans.
- In browser-local mode, public shipments are stored only in that browser (`LOCAL-12345` and the 12-digit Express-style sample `748512903645` are seeded with the demo workspace). They are trackable after sign-out in the same browser, but not from another device. Cross-device public tracking uses the server-backed database mode described below.
- Profiles, addresses, plans, settings, and the last 100 local activity entries are saved under `fedexr:workspace:v1`. A tab-scoped session uses `fedexr:workspace-session:v1`; sign-out clears the session, not records. Storage failures are reported without claiming that a write succeeded. Malformed saved data is safely ignored.
- New workspace passphrases are 10–128 characters. Web Crypto derives a 256-bit PBKDF2-SHA256 hash using a fresh 16-byte salt and 210,000 iterations; no plaintext passphrase or default password is saved. Old access flags and the old plaintext administrator password are removed. Suspension or a credential change in another tab invalidates that tab's active access; activation requires signing in again.
- This is **browser-local access, not production authentication**. Browser owners can inspect/alter local records and roles. Local UI gates are not server authorization, records are not encrypted, profiles are not verified carrier identities, and email is not sent. Never reuse FedEx credentials or put payment information here. Production accounts require a separate configured backend, server-managed sessions, and server-enforced authorization.
- Tracking image attachments now use the private shared API described in [`server/IMAGES.md`](server/IMAGES.md). Server administrators can upload/load/change visibility/remove images using their account session; members can only read explicit assignments. Browser-local profiles and reference knowledge do not authorize files. Optional operator-key access is disabled by default, is header-only, requires a separate strong key, and never grants member ownership. The server validates and re-encodes JPG/PNG bytes, strips metadata, applies size/pixel limits, and never creates tables inside HTTP requests. A reviewed migration copies valid images from either historical schema into an event-keyed private table while preserving the original archive.
- The shipment wizard's final stage is review, not payment. Guests can download a planning brief; signed-in profiles can save/update a local plan and use their own saved U.S. addresses. No card fields, fake completion, shipping label, or invented tracking number remain. Package photos are validated locally and their object URLs revoked; photos are not uploaded/persisted or embedded in downloads. Saved records contain recipient, ZIP codes, weight, service, date, and package notes; full address details belong in the separately downloaded brief.

## Server-backed accounts (explicit opt-in)

The new account service reuses an existing PostgreSQL database and adds only `fedexr_*` tables. Better Auth handles verified-email registration, signed HttpOnly sessions, recovery, and password changes. The shared-record API enforces ownership, active status, and administrator permissions on the server. Local browser roles are never imported or trusted by it. The additive `003-public-shipments.sql` migration adds `fedexr_public_shipments`, `004-public-shipment-operations.sql` adds administrator-only internal-note and archive fields, and `005-public-shipment-auto-progress.sql` adds automatic-progression settings; administrator-only `/api/workspace/shipments` mutations write it, assigned members receive their active records in the workspace snapshot, and unauthenticated `GET /api/tracking/:number` returns only public-safe shipment fields (with account identifiers and internal notes removed).

The default preview remains clearly labeled browser-local until private server configuration is supplied and the additive migration is reviewed/applied. Setting `VITE_WORKSPACE_MODE=server` enables the wired server provider; an unavailable API fails closed instead of accepting local profiles. No live database, SMTP provider, migration, or deployment was configured automatically.

See [`server/README.md`](server/README.md) and the sanitized [`.env.example`](.env.example) for secure setup, migration review, first-admin provisioning, cookie/origin behavior, API routes, and test/deployment instructions. Never paste connection strings, signing secrets, or mail credentials into chat or `VITE_*` settings. Private attachment setup and cutover are documented in `server/IMAGES.md`.

## Optional official FedEx API (side-by-side)

The local/application shipment registry and the official FedEx integration are deliberately independent. Set the private server settings `FEDEX_ENV` (`sandbox` by default, or `production`), `FEDEX_CLIENT_ID`, and `FEDEX_CLIENT_SECRET` from a FedEx Developer Portal project. Credentials and the account number are read only by `server/src/fedex.js`; they are never sent to the browser, and status responses expose only booleans, the environment, and missing setting names.

With those settings present, `GET /api/carrier/track/:number` uses FedEx OAuth and the Track API for numeric references, normalizes the carrier response to status/service/latest-location/dates/events, and the public tracking page shows it beside—never merged with—the application record. Sandbox mode returns FedEx test data; production mode returns live carrier data. Without the settings, the panel says the API is not connected and the application record keeps working.

Official shipment creation is a second, explicit opt-in: set `FEDEX_ACCOUNT_NUMBER` and `FEDEX_CREATE_SHIPMENTS_ENABLED=true`. In server mode, the administrator Overview then shows a guarded **Create official FedEx shipment** form for U.S. shipper/recipient address, phone, service, packaging, pickup, date, weight, and label format; the administrator must confirm the submission before it calls `POST /api/carrier/shipments`. The endpoint requires a verified server administrator session, validates the details, calls the FedEx Ship API, and returns the carrier-issued tracking number and label reference. The result links to side-by-side tracking and is not automatically merged into the application’s public-shipment registry. In production that can create a real, billable shipment, so it stays disabled by default and is not triggered by creating an application shipment.
